# P1-T14 / P1-T16: self-host scripts, images, release pipeline

Date: 2026-10-08. Branch `task/P1-T14-T16-deploy-release`. Spec: docs/spec/part4.md 4.9 (4.9.8 to 4.9.10), 4.15.4.

## D-a: Operator scripts share deploy/lib.sh; data operations run inside the api image (stackctl.py)

Decision: `bootstrap.sh`, `backup.sh`, `restore.sh`, `upgrade.sh` and `smoke.sh` source `deploy/lib.sh` (one
`compose()` wrapper that applies the env file and extra compose files, env file editing, random secrets,
readiness polling). Anything that touches the database, `keys.json` or blobs runs `deploy/stackctl.py` in a
one-off `docker compose run --rm --no-deps -T api` container. The script travels base64-encoded in argv, so
there is no bind mount and no host path translation (Git Bash, Docker Desktop and Linux behave the same),
and tar data streams over stdin/stdout, so host file ownership never matters.
Why: the container sees exactly the API's volumes, settings (`ezmd_api.settings.Settings` resolves the paths)
and Python; the host needs only bash, coreutils, tar, curl and Docker.

## D-b: Backup format and scope

`ezmd-<UTC ts>.tar.gz` = `app.tar` (stackctl: SQLite online-backup snapshot checked with
`PRAGMA integrity_check`, `keys.json`, blobs, `manifest.json` with SHA-256 and size per file),
`caddy_data.tar`, `env`, `SHA256SUMS`. Restore verifies both layers before stopping anything, rejects
non-regular members, absolute paths, `..` and unknown prefixes, stages on the destination volumes and swaps.
Deviation from part4 4.9.9: blobs ARE included by default (the task requires that a job's result survives
a wipe; results expire after 24 h anyway), `--no-blobs` restores the spec's behavior. Default backup dir
`deploy/backups` (not `/var/backups/ezmd`) so the scripts run without root; `EZMD_BACKUP_DIR` overrides.
Postgres/S3 are out of scope (stackctl refuses a non-SQLite database).

## D-c: keys.json lives in the state volume; bootstrap creates it with an owner key

`EZMD_KEYS_FILE=/var/lib/ezmd/keys.json` (set by bootstrap when empty). A bind-mounted `./keys.json`
(spec) becomes a directory when the file is missing, and the API refuses to start on a missing keys file;
inside the volume it is owned by uid 10001 and covered by the same backup. The owner key is written once to
`ezmd-owner.key` (mode 600) next to the env file.

## D-d: Bootstrap scope: the stack, not the host

Bootstrap does env file, secrets (generated only when empty; never rotated), pull or `--build`, migrations,
keys, `up --wait`, `/readyz`, smoke. Host provisioning from 4.9.8 (Docker install, ufw, Cloudflare-only
DOCKER-USER rules, fail2ban, sshd, unattended upgrades, systemd units) is left for the Phase 4 public
instance runbook: it is not testable here and is destructive on a workstation. `--plain-http` added for
local use; a template still holding `ezmd.example.com` is refused so nothing asks Let's Encrypt for it.

## D-e: Migrations: bootstrap puts fresh databases under Alembic; create_all databases are skipped

The API runs `create_all` at startup, which leaves no `alembic_version` table; `alembic upgrade` would then
fail on existing tables. `stackctl migrate` upgrades fresh or Alembic-managed databases and warns and
skips otherwise. Bootstrap migrates before the first start, so bootstrapped installs are Alembic-managed.
Core change request (apps/api, not owned here): run `ezmd_api.migrate.upgrade` at API startup (or
`create_all` + `alembic stamp head` on an empty database) so every install is migratable.

## D-f: Upgrade rollback restores the pre-upgrade backup when migrations ran

Migrations are forward-only, so a failed upgrade after `migrate` restores the backup taken in step 1 and
starts the previous `EZMD_VERSION`. Upgrade never builds from source (`--no-build`, and every image must
exist locally after the pull). A version argument is required (no "latest tag" discovery).

## D-g: Compose pins the data paths; env file path is selectable

`EZMD_DATA_DIR` and `EZMD_BLOB_FS_ROOT` are set in `environment:` (which beats `env_file:`). Before,
env.example's empty `EZMD_BLOB_FS_ROOT=` overrode the image's ENV, Settings ignored the empty value, and
blobs silently went to `/var/lib/ezmd/blobs` in the state volume while the `blobs` volume stayed empty.
`env_file` is `${EZMD_ENV_FILE:-.env}` so scripts and CI can use an env file outside the checkout (this
machine also denies agents access to `.env*` files, D-0018).

## D-h: API image budget 480 MB -> 600 MB (revisits D-0012)

Measured: api 556 MB, worker 888 MB (local build, sum of uncompressed layers, after removing numpy's
test suite, about 18 MB, from the shared venv). The wave-1 converters' default dependencies (lxml,
pikepdf, pypdfium2, trafilatura and its babel/dateparser chain, openpyxl, Pillow) add about 100 MB.
The API cannot drop them: it does not convert in compose (`EZMD_QUEUE=rq`; the inline queue is the
single-process `ezmd serve` path), but it loads the same converter registry as the workers for
`/v1/capabilities` (`loaded`, `extras`) and for `ircache.converter_version`, which feeds the IR cache key
used by dedup in `routes/convert.py`. Without the dependencies the registry would hold `Unavailable`
entries, capabilities would be wrong and the API's cache keys would no longer match the workers'.
Splitting that metadata out of the registry is a core change (not owned here). So the api image keeps the
default install and the budget becomes 600 MB; worker stays 1200 MB.

## D-i: Worker extras

The worker image adds the `data` extra (pyarrow, Apache-2.0) via build arg `EZMD_WORKER_EXTRAS` (default
`data`); `docs` (Docling) is opt-in because the universal lock resolves CUDA torch on Linux (several GB;
needs a CPU-torch index pin before it can be a default). `nonfree` and `7z` are refused at build time.
`EZMD_WORKER_APT_PACKAGES` adds e.g. LibreOffice. Fixed a latent bug: `-name '*.so*'` matched pyarrow's
test data `*.some-named-index.parquet` and `strip` failed.

## D-j: Release pipeline (P1-T16)

- `images.yml` (reusable): per target, push by digest only, Trivy scan of that digest (HIGH/CRITICAL with
  a fix fail), syft SPDX SBOM, cosign keyless `sign` + `attest --type spdxjson`, and only then
  `imagetools create` the tags. BuildKit provenance (`mode=max`) and SBOM attestations as well. Release
  candidates get no `:latest`/`:X.Y` tags.
- `release.yml`: `preflight` (tools/release_version.py: tag must be `vX.Y.Z` or `vX.Y.Z-rcN` and match the
  three Python packages' versions, PEP 440 `X.Y.ZrcN`; final tags also the npm SDK), `verify` (ci.yml),
  images, dists, `publish-gate`, TestPyPI (rc only, environment `testpypi`), PyPI, npm, MCP registry (final
  only, environment `release`), extension, GitHub release with dists, SBOMs and SHA256SUMS.
- Human gate, two locks: repository variable `EZMD_PUBLISH_ENABLED=true`, and `publish-gate` fails the run
  if environment `release` lacks a `required_reviewers` rule (an environment auto-created on first use has
  none). OIDC trusted publishing only; a test asserts no secret other than `GITHUB_TOKEN` is referenced.
- mcp-publisher pinned to v1.8.1 with its SHA-256; npm via `npx npm@11.21.0` (trusted publishing needs
  npm >= 11.5). New actions pinned by SHA: sigstore/cosign-installer v4.1.2, anchore/sbom-action v0.24.3.
- ci.yml smoke job now shellchecks deploy/*.sh, runs bootstrap, then backup, `down -v`, restore, and asserts
  the earlier job, its result and the owner key survive (part4 4.9.10 integration test).
