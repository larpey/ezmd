# P1-T09: CLI decisions

Scope: docs/spec/part4.md 4.2 (convert, batch, doctor, serve, capabilities, version, detect, completion).
Code: `packages/core/src/ezmd/cli/` (app, convert, batch, doctor, info, config, output, remote,
exitcodes, options). Tests: `packages/core/tests/cli/`.

## Approach note (spec part1 2.5)

- Libraries: `typer` 0.27.3 (MIT) on `click` 8.5 (BSD-3), `rich` (MIT), `httpx` (BSD-3), stdlib `tomllib`.
  All were already core dependencies; no new dependency was added, so there are no dependency lines.
- Entry point: the `ezmd` console script (`ezmd.cli:app`, unchanged in `packages/core/pyproject.toml`).
- Known issue: click 8.2+ turns Ctrl-C into `Abort` (exit 1, "Aborted!"). Mitigation: `convert` and `batch`
  catch `KeyboardInterrupt` themselves and exit 130.
- Known issue: typer's `--show-completion` ignores its shell argument unless shell detection is disabled;
  `--install-completion <shell>` and `--show-completion` (detected shell) both work. Tests use typer's
  `_TYPER_COMPLETE_TEST_DISABLE_SHELL_DETECTION` switch with a temporary home directory.

## Decisions

1. **Thin client.** `convert` and `batch` call `ezmd.library.convert` / `Options` / `Result.render` only;
   `capabilities` calls `ezmd.library.capabilities`. With `--remote` the CLI uses the REST API. No
   conversion logic lives in the CLI (part4 4.0 rule 1). `tests/test_cli_exit_codes.py` now patches
   `ezmd.library.convert_ref`, the function the library actually calls.
2. **Profile default (4.0 rule 3).** `--profile` > `EZMD_PROFILE` > `defaults.profile` in the config file >
   automatic. Automatic means `compact` only when Markdown goes to an interactive terminal (no `--out`,
   no `--json`, stdout is a TTY) and `full` otherwise (file output, piped or redirected stdout, `--json`).
   `batch` defaults to `full`.
3. **Formats.** `md`, `txt`, `json` render locally; `docx` and `srt` are accepted names in the contract but
   exit 2 with "not yet supported".
4. **Sidecar.** On by default for `--out` (config `defaults.sidecar`, env `EZMD_SIDECAR`), off with
   `--no-sidecar`. It is written as `<stem>.ezmd.json` (same name as `Result.save`). It is not written for
   `--format json`, which already embeds the sidecar, or for profiles without one (`compact`).
5. **`--out DIR`.** Writes `<title>.<ext>` where the title is the frontmatter title passed through a
   filename sanitizer (NFKC, no separators or control characters, no Windows reserved names, max 80
   chars), falling back to the input stem. A path that exists as a directory or ends in a separator is a
   directory.
6. **`--engine family=name`.** Mapped to `Options.converter` only when exactly one registered converter
   matches (tiers: exact id `name`; id `family.name`; ids containing segment `name` with family `family`;
   last segment `name`). No match or several matches exit 2. One `--engine` per call, because `Options`
   forces a single converter. The config `[engines]` table is read and validated but not applied: applying
   a per-family preference to every input needs per-family engine selection in core (see "Core change
   requests").
7. **`--json`.** Exactly one JSON object on stdout, also on failure: `status: "failed"`, `exit_code`,
   `error {code, message}`, and the failure as an error-severity entry in `warnings`. Human output
   (progress, warnings, notes) goes to stderr. In non-JSON mode warnings print to stderr as
   `WARN [code] message` after the output; `--quiet` suppresses progress and warnings.
8. **Progress.** A transient Rich bar on stderr only when stderr is a TTY and neither `--json` nor `--quiet`
   is set. Labels are the job states the web UI and SSE use (Queued, Fetching, Converting, Rendering), plus
   the converter's own progress messages; remote runs show the polled job state.
9. **Exit codes** (4.2.2): mapping in `ezmd/cli/exitcodes.py`. Local: executables and "not supported yet"
   and `experimental_disabled` exit 6; `InputTooLarge`/`ResponseTooLarge` 5; `ResidentialOnly`,
   `PlatformDisabled`, `FetchRequired` 4; other fetch errors and converter failures 1; bad options, unknown
   profile/format, missing file, bad config 2; usable result with an error-severity warning 3 (D-0017);
   Ctrl-C 130. Remote: the Part 1 7.5 error codes map the same way (`unsupported_media_type` 6,
   `input_too_large`/`result_too_large` 5, `platform_disabled` and a `needs_user_action` job 4,
   `invalid_request`/`unauthorized`/`forbidden`/`not_implemented` 2, everything else 1).
10. **Remote.** `POST /v1/convert?wait=30&format=json` (multipart `file` + `options` + `profile` for paths
    and stdin; JSON `{url, profile, options}` for URLs). A 200 with `X-Ezmd-Job` is the finished result;
    otherwise poll `GET /v1/jobs/{id}` every 0.5 s (cap 1 h) and fetch `GET /v1/jobs/{id}/result?format=json`.
    `--format txt` fetches the `txt` rendering separately. Warnings come from the sidecar when the profile
    has one, else from the frontmatter codes with the registry description. Headers:
    `User-Agent: ezmd-cli/<version>`, `X-API-Key` from `EZMD_API_KEY` or `[remote] api_key`. Redirects
    are not followed (the key is never sent to another host).
11. **Batch idempotency.** The input's SHA-256 is compared with the previous run's record: first the
    previous manifest line for that input (`sha256` plus same `profile` and `format`, status
    converted/partial/skipped), then the sidecar (`frontmatter.source_hash == "sha256:<hex>"` and same
    `profile`). The output file must still exist. The spec's "matching `content_hash` in the sidecar"
    cannot work as written because `content_hash` hashes the output, which is unknown before converting;
    `source_hash` is the input hash the sidecar already records. Manifest lines carry `path, status, out,
    warnings, seconds, tokens` plus `sha256, profile, format` (and `error` on failure). The manifest
    defaults to `<out>/manifest.jsonl` and is rewritten each run, streamed line by line. A skip-only re-run
    of 101 files takes well under a second in the test (asserted < 5 s to stay robust on slow CI).
12. **Batch execution.** One worker (or one pending file) runs in-process; more use a
    `ProcessPoolExecutor` (spec: process pool) whose task calls `ezmd.convert`. Default workers
    `min(cpu - 1, 8)`, at least 1. Without `--continue-on-error` the first failure stops the run (pending
    files are recorded as `cancelled`) and exits 1; with it, failures exit 3. `partial` results count as
    converted. Inputs: a directory (top level, or the whole tree with `--recursive`), a glob (mirrors from
    the glob's fixed prefix), or a single file. Dotfiles, `*.ezmd.json`, the manifest, the output tree,
    and outputs listed in the previous manifest are never inputs. Stems that collide in one directory
    (`a.txt`, `a.md`) keep their full names (`a.txt.md`, `a.md.md`). `--out` is required unless
    `defaults.out_dir` is set in the config file.
13. **Config.** Location: `EZMD_CONFIG`; else `%APPDATA%/ezmd/config.toml` (Windows),
    `~/Library/Application Support/ezmd/config.toml` (macOS), `$XDG_CONFIG_HOME/ezmd/config.toml` or
    `~/.config/ezmd/config.toml`. Read with `tomllib`. Applied keys: `defaults.profile|format|out_dir|
    sidecar`, `remote.url|api_key`, `limits.max_file_mb` (to `Options.max_bytes`) and
    `limits.max_duration_s` (to `Options.max_duration_seconds`). `fetch` and `watch` keys are validated
    for type but unused in Phase 1. Environment: `EZMD_PROFILE`, `EZMD_FORMAT`, `EZMD_REMOTE` (an
    empty value forces in-process), `EZMD_API_KEY`, `EZMD_SIDECAR`. Flags override both. Invalid TOML,
    a wrong type, an unknown profile/format, or an `EZMD_CONFIG` that does not exist exit 2; unknown keys
    print a note to stderr.
14. **Doctor.** Rows: python, ezmd, each extra (WARN when absent), ffmpeg/ffprobe (required by `media`,
    version via `ezmd.core.sandbox.run`), pandoc and LibreOffice (optional, WARN), libmagic (WARN; detection
    falls back to Magika), Magika model (core), cache dir writability and free space (core), config dir
    writability (WARN; tested on the nearest existing ancestor so doctor never creates it), Redis when
    `EZMD_REDIS_URL` is set, Docling import when the `docs` extra is present. An extra counts as
    installed when a marker package is importable (`docling`, `faster_whisper`/`ctranslate2`,
    `rapidocr_onnxruntime`, `crawl4ai`, `yt_dlp`, `ezmd_api`, `ezmd_mcp`) or when the installed
    `ezmd` metadata declares the extra and all of its requirements are present. Exit 2 only for a
    MISSING row required by core, by configuration (Redis), or by an installed extra. CUDA/ROCm/MPS, ASR/OCR
    model cache sizes, and yt-dlp/Deno rows wait for the extras and `models` registry (Phase 2).
15. **Version.** `version` prints version, commit, and build date, read from `ezmd/_build_info.json`
    (to be written by the release build), then the install's `direct_url.json` VCS commit, then the source
    checkout's `.git` files (worktrees and packed refs handled, no subprocess). Unknown values print
    `unknown` (`null` with `--json`).
16. **Help budget.** Every `--help` fits in 40 lines at 100 columns, with and without Rich (tested).

## Core change requests (not made; outside this task's ownership)

- `tools/gen_cli_doc.py` `EXIT_CODES` is stale: row 2 still says "or a result with an error-severity
  warning" (that is exit 3 since D-0017), and there is no row for 3. Suggested rows:
  `("2", "Bad arguments, missing file or dependency, or invalid config.")` and
  `("3", "Partial success: a usable result with an error-severity warning, or a batch with failures under --continue-on-error.")`.
  Then regenerate `docs/cli.md`.
- Per-family engine preference (`[engines]` config, `--engine` for one family without forcing every
  input): add an `Options.engines: dict[str, str]` field that the registry uses to order a family's chain.
- `Options.load_user_config` (part4 4.3.2 item 4) is not on `ezmd.Options`; the CLI reads the config
  itself, which meets the intent (library stays deterministic).
