# P1-T04: email converters (communication family)

## Approach note (spec part1 2.5)

- Libraries: Python stdlib `email` (`policy.default`, `BytesParser`), `mailbox.mbox`, and `charset-normalizer`
  (MIT, already a default dependency) for undeclared or wrong charsets. HTML bodies use the web family's
  `intomd_converters.web.pipeline.build_document` in `full_body` mode.
- MSG default: olefile 0.47 (2023), BSD-2-Clause, LICENSE.txt verified at
  https://github.com/decalage2/olefile/blob/v0.47/LICENSE.txt (two redistribution clauses, no
  non-endorsement clause). Entry point `olefile.OleFileIO(bytes)`. Known issue: a bytes argument shorter than
  `MINIMAL_OLEFILE_SIZE` (1,536) is treated as a file name; `msg_native.open_ole` checks the length and the
  magic first. On top of it: a native MS-OXMSG property reader, an MS-OXRTFCP decompressor (verified against the
  spec's worked example, CRC included), and an MS-OXRTFEX HTML de-encapsulator.
- MSG fallback: extract-msg 0.56.1 (2026-08-14), GPL-3.0, LICENSE.txt verified at
  https://github.com/TeamMsgExtractor/msg-extractor/blob/master/LICENSE.txt. Entry point
  `extract_msg.openMsg(path, strict=False)`. Only in the `nonfree` extra, with `notify_once("extract-msg")` on
  import of `comms.msg_engine`. Open issues #480 and #489 (UnicodeDecodeError on `htmlBody`) are handled by a
  broad catch on open plus our own decoding. A privately reported security issue (#487) is one more reason to
  keep it out of the default install.
- Entry points: `comms.eml`, `comms.mbox`, `comms.msg` (native), and `comms.msg_extract` (extract-msg, or
  `Unavailable` with `requires_extras=("nonfree",)`). Chain `application/vnd.ms-outlook -> [comms.msg,
  comms.msg_extract]`.
- Mitigations:
  - Header values are cut at `max_header_chars` (16 KB) everywhere: tables, sidecar, and the warning agree.
  - The MIME walk is bounded at 32 levels and 1,000 parts, and a `RecursionError` becomes a parse failure.
  - Attachments go through `ctx.convert_child` (shared deadline, depth limit), with caps of 100 MB per
    attachment, 200 attachments per message, and 5,000 messages per mailbox.
  - Attachment names are reduced to a cleaned basename.
  - mboxrd `>From ` lines are unescaped, and unescaped `From ` splits are merged back.
  - MSG: 1,000 recipient/attachment storages, 16 MB per property stream, oversized attachments listed without
    being read, and compressed RTF capped at 64 MB of output.
- Fallback:
  - An HTML body falls back to the plain part, then to visible text when the web family is missing.
  - MSG falls back from the native reader to extract-msg when that is installed.
- Fixtures (self-generated by `fixtures/comms/_generate.py`, CC0): eml-plain-flowed, eml-html-only,
  eml-alternative-cid, eml-attachments, eml-forwarded, mbox-threads, eml-broken-charset, eml-hostile, and
  msg-outlook. msg-outlook is built with `fixtures/comms/_cfb.py`, a minimal MS-CFB v3 writer with a mini stream
  and a balanced sibling tree (olefile cannot create files). It holds a compressed-RTF body that encapsulates
  HTML, transport headers, recipients, two attachments, and an embedded message.
- Threshold: 0.97 for `comms.eml`, `comms.mbox`, and `comms.msg` (spec 9g: body text_similarity 0.97, headers exact).

## Decisions

- Family id `comms` (registry FAMILIES; spec section 9 is "communication"). The package is
  `intomd_converters.comms` so ICS, VCF, and chat exports can join it later.
- MSG default is the spec's native olefile reader (part2 9b step 2; Part 2 is authoritative for converter detail
  per D-0002). `olefile` moved out of `[nonfree]` in `tools/license_allowlist.toml`; it was listed there only
  because extract-msg depends on it. An override entry is in `tools/license_overrides.toml`, because the metadata
  carries only the ambiguous "BSD License" classifier. `docs/licenses.md` is updated. extract-msg stays as the
  opt-in GPL engine, second in the chain.
- HTML bodies go in-process through the web pipeline, not through `ctx.convert_child`. A body is part of the
  message: going through the child path would count it against `max_attachment_depth`, drop it when
  `follow_attachments=False`, and let article extraction remove quotes and signatures. Block ids are prefixed
  per message.
- Forwarded `message/rfc822` parts go through `ctx.convert_child`. Embedded Outlook messages are parsed
  in-process, because they are storages, not byte streams.
- Plain-text line structure (golden reviews 1 and 2): one shared implementation,
  `intomd_converters.text.lines.join_lines`, used by `text.plain` and the email bodies. Inside a blank-line
  run, a line continues the previous one when the previous line is full width (60+ characters) or the line
  starts lowercase (part2 section 2 step 22(7) plus failure mode 10). List items and indented code lines never
  join into or absorb another line. `format=flowed` input is already unwrapped (RFC 3676, DelSp,
  space-stuffing), so nothing is joined. A run that keeps more than one line (verse, addresses, `Key: value`,
  `Thanks,` / `Ann`) becomes one Paragraph with `attrs["line_breaks"] = "hard"`, not one paragraph per line.
  `text.plain` keeps its source newlines byte for byte when a run is a single wrapped paragraph. No non-comms
  golden changed in Markdown or in sidecar block text and attrs.
- Core renderer: `Paragraph.attrs["line_breaks"] = "hard"` renders as CommonMark hard breaks (backslash at
  line end) in Markdown and as newlines in txt (`render/blocks.py`, `render/plaintext.py`, with a test). This was
  needed: span newlines otherwise collapse into spaces, which was the booking.txt reject.
- Core renderer (`render/children.py`, minimal, with a test in
  `packages/core/tests/render/test_render_family_requests.py`): child headings shift uniformly. The
  shallowest remaining heading lands one level below the child's section heading, and the others keep their
  distance from it. Before, both H1 and H2 mapped to the same level, which flattened a DOCX with several H1s.
  Only comms/eml-attachments changed among existing goldens.
- Core detection (`detect.py`, part2 9a): `rfc822_evidence` needs a leading header block in which every line is
  a header field or a folded continuation, one field being `From:`. It counts the mail-only fields
  (Message-ID, Received, MIME-Version, Return-Path); Date and Subject count for nothing. A textual Magika or
  libmagic guess becomes `message/rfc822` with one such field, or two when the extension names another
  text-like format (.md, .txt, .rst, .html, ...). `notes.md` with `Title:/From:/Date:` stays Markdown, an HTTP
  header dump stays text, and a real message saved as .html/.txt/.dat or with no extension is detected.
  `comms.eml` uses the same rule in `can_handle`.
- Over-long headers are cut at an address boundary (address headers) or a word boundary, 80 characters under
  the cap, with an inline marker: `… (N more recipients truncated)` or `… (N characters truncated)`. Removed
  control/bidi/invisible characters in headers (decoded CR/LF included) are reported as
  `removed_hidden_elements` with `detail.where="headers"`.
- Embedded Outlook messages report their size as the sum of their storage's streams.
- Bcc is rendered when present, because spec 9c step 1 lists it.
- Roles are block attrs (`attrs.role` = `reply_header` / `reply_history` / `signature`).
- Charset warnings use the existing `encoding_uncertain` with `detail.reason`: `declared_charset_mismatch`
  when a declared body charset fails, and `unknown_header_charset` for encoded words in an unknown charset.
  Mislabeled 8-bit bodies prefer cp1252 when it is within 0.1 chaos of charset-normalizer's best guess.
- Mailbox truncation uses `truncated` (`detail.reason="max_messages"`) and `size_cap`. No new warning codes.

## Dependencies

- olefile, `>=0.47,<0.48`, BSD-2-Clause, wheel 114 KB, default install. Reads the OLE2/CFB container of Outlook
  `.msg` files.
- extract-msg, `>=0.56.1,<0.57`, GPL-3.0, wheel 338 KB (pulls compressed-rtf, RTFDE, beautifulsoup4, tzlocal,
  ebcdic, red-black-tree-mod), `nonfree` extra only. The fallback MSG engine.

## Core changes made here
